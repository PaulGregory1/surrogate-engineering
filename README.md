# flow-surrogate

A 2-D lattice-Boltzmann solver, five surrogates fitted to it, and a shape optimiser
that back-propagates through the surrogate to minimise drag at constant area — then
checks the answer against the solver.

Everything runs on a laptop: ~25 min to generate the dataset, minutes per model to
train.  Numbers are in [`RESULTS.md`](RESULTS.md), regenerated by `scripts/03_report.py`.

---

## 1. The expensive model

`flowsurrogate/lbm.py` — D2Q9 BGK lattice Boltzmann on a 192x96 lattice: bounce-back
on the obstacle, free-slip channel walls (so no wall boundary layer contaminates the
wake), equilibrium inlet, zero-gradient outlet, drag and lift from the
momentum-exchange method.  Fields are time-averaged over the last 2500 of 9000 steps
and the residual drift over that window is stored with every sample, so unconverged
cases are visible rather than silently averaged in.

Two things make it usable as a data generator on a laptop:

- **the batch dimension is a design dimension** — B geometries are marched in
  lock-step, which turns a latency-bound stencil into a bandwidth-bound one;
- **the whole time step is one `torch.compile` region**.  Eager mode issues ~40
  kernels per step over a 40 MB state.  Fusing them, plus replacing two
  index-tensor gathers by constant slices, took the solver from **6.7 to 1.7 s per
  sample** (3.9x) with bit-identical output.

### Verification

Before fitting anything to a solver it is worth knowing whether the solver is right.
`scripts/01_validate_solver.py` runs steady flow past a circular cylinder and compares
against published values for an unbounded cylinder (C_d = 2.05 at Re = 20, 1.55 at
Re = 40; Tritton 1959, Fornberg 1980), after the standard blockage correction
`C_d,inf ≈ C_d (1 - β)²`:

| grid | blockage β | Re | C_d raw | corrected | reference |
|---|---|---|---|---|---|
| 288x192 | 10.4 % | 20 | 2.540 | **2.04** | 2.05 |
| 288x192 | 10.4 % | 40 | 1.894 | **1.52** | 1.55 |
| 192x96 (production) | 20.8 % | 20 | 3.127 | **1.96** | 2.05 |
| 192x96 (production) | 20.8 % | 40 | 2.330 | **1.46** | 1.55 |

Within 2 % on the wider grid and 6 % on the production grid, with the residual gap in
the direction you would expect from a 20-cell-diameter body.  The surrogates are
fitted to *this* solver, not to reality, and the report says so; but it is a solver
whose error is known.

## 2. The dataset

`scripts/00_generate_data.py`.  The obstacle is a star-shaped body, `r(θ) = r0 (1 +
Σ a_k cos kθ + b_k sin kθ)` for k = 2, 3, 4 — six coefficients plus a scale, with the
k = 1 modes dropped because they are a rigid translation.  The area has a closed form,
which the optimiser later uses to enforce the area constraint exactly instead of by
penalty.

| split | n | what it is |
|---|---|---|
| `train` / `val` / `test` | 640 / 64 / 128 | Re ∈ [30, 110], coefficients in ±0.16 |
| `ood` | 64 | Re ∈ [110, 150], coefficients in ±0.24, wider radii — deliberately outside the training box |

Targets: time-averaged `u`, `v`, `p` and the drag coefficient (referenced to the
equivalent diameter, so the area constraint fixes the reference length).

## 3. The surrogates

All five see the same data and are scored on the same held-out geometries.

| model | input | why it is here |
|---|---|---|
| **POD + ridge** | 7 shape parameters + Re | the reduced-order model an engineering team builds first |
| **POD + kernel ridge** | idem | the same, done properly — a genuinely strong baseline on a 7-D design space |
| **U-Net** | rasterised level set + mask + Re | geometry-agnostic: never sees the parametrisation |
| **U-Net + continuity loss** | idem | adds `‖∇·u‖²` on the de-normalised prediction |
| **FNO** | idem + coordinates | the standard neural-operator answer |

The POD baselines are not a formality.  On a 7-parameter family they are hard to beat
in-distribution, and saying so is the point: the case for a geometry-aware network is
not that it wins the interpolation benchmark, it is that it is not welded to one CAD
parametrisation — which is what the OOD split and the shape-optimisation section
actually test.

Every model has two heads, fields and drag, and is scored on three things that
disagree with each other: field error, drag error (the engineering quantity), and a
continuity residual `mean|∇·u| L/U` — a surrogate can have a small MSE and still
produce a velocity field that does not conserve mass.

## 4. Shape optimisation

`scripts/04_optimize_shape.py` — the reason the whole thing is differentiable.

Minimise drag at **exactly** constant area.  The scale `r0` is derived from the
harmonic coefficients so that the area constraint holds by construction: no penalty
weight, no infeasible iterates, six free parameters.  Gradients flow from the drag
head, through the network, through the rasterised level set, back to the
coefficients.

One detail matters: the networks are trained on a hard occupancy mask, which has zero
gradient everywhere.  At optimisation time it is replaced by `sigmoid(-φ/ε)` with
ε below one cell — numerically the same image (the two disagree only within ~1.5 cells
of the boundary, which `tests/test_pipeline.py` checks), but the boundary now moves
when the coefficients move.

The optimiser runs 16 starts in parallel, projected onto the training box.  Then:

1. the optimised designs are re-run through the LBM — the gap between what the
   surrogate promised and what the solver delivers is reported, not hidden;
2. one round of **active learning** folds those solver-labelled designs back into the
   training set and fine-tunes, because the optimiser has just told us exactly where
   the surrogate is being trusted.

## 5. Limitations

- The flow is 2-D, laminar, and time-averaged; nothing here says anything about
  turbulence modelling.
- A 20-cell body diameter under-resolves the boundary layer; the solver is verified
  to a few percent, not to benchmark accuracy.
- The level set is radial (`ρ - r(θ)`), not a true Euclidean distance field.  It is
  exact on the boundary and monotone across it, which is what the networks need, but
  a genuine SDF would be a better input for non-star-shaped geometries.
- Drag is a scalar head rather than an integral of the predicted surface stress.  The
  integral would be more physically consistent and is the obvious next step.

## 6. Running it

```bash
uv venv --python 3.12 .venv && VIRTUAL_ENV=.venv uv pip install -e .
./.venv/bin/python run_all.py            # everything, ~2 h on an M-series laptop
```

or step by step:

```bash
python scripts/00_generate_data.py       # ~25 min  -> data/
python scripts/01_validate_solver.py     # ~4 min   -> results/solver_validation.json
python scripts/02_train_all.py           # ~60 min  -> runs/
python scripts/03_report.py              #          -> RESULTS.md, figs/
python scripts/04_optimize_shape.py      # ~6 min   -> results/optimization.json
python -m pytest tests -q
```

Add `--device cpu` anywhere to avoid MPS.  `scripts/02_train_all.py --epochs 20
--skip-sweep` gives a usable smoke run in a few minutes.

## 7. Layout

```
flowsurrogate/
  geometry.py    star-shaped bodies; NumPy path + differentiable Torch path
  lbm.py         batched, compiled D2Q9 solver
  data.py        generation, splits, normalisation, input channels
  models/        pod.py (ROM baselines), unet.py, fno.py
  train.py       shared training loop (masked loss, drag head, physics term)
  metrics.py     field / drag / continuity metrics
  evaluate.py    predictions -> numbers
  optimize.py    differentiable shape rendering + projected Adam + solver verification
  plots.py       figures
scripts/         00 generate, 01 validate, 02 train, 03 report, 04 optimise
tests/           geometry, solver, pipeline
```
