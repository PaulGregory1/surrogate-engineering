# stress-gnn

A finite-element solver for perforated brackets, a graph network that predicts the
**fine-mesh** stress field from a **coarse** mesh, and a study of whether that
surrogate ranks candidate designs better than simply solving on the coarse mesh.

Everything runs on a laptop: ~20 min to generate the dataset, ~2 min per model to
train.  Numbers are in [`RESULTS.md`](RESULTS.md), regenerated by `scripts/03_report.py`.

---

## 1. The premise

A 2 x 1 plate with 2-4 circular holes, clamped on the left, loaded on the right.
`scripts/01_validate_fem.py` measures what a coarse mesh costs you (errors relative to
h = 0.008, averaged over 12 designs):

| h | nodes | mesh + solve | peak von Mises err | compliance err |
|---|---|---|---|---|
| 0.060 | 787 | 0.04 s | **-28.4 %** | -2.60 % |
| 0.045 | 1 350 | 0.05 s | **-24.7 %** | -1.64 % |
| 0.030 | 2 897 | 0.10 s | -17.3 % | -0.79 % |
| 0.020 | 6 318 | 0.24 s | -11.6 % | -0.35 % |
| 0.014 | 12 808 | 0.55 s | -7.1 % | -0.14 % |
| **0.010 (reference)** | 24 772 | 1.20 s | -3.2 % | -0.04 % |
| 0.008 | 38 598 | 2.13 s | 0 | 0 |

That table is the whole project.  Compliance — an energy — is converged to under 3 % on
the coarsest mesh; the peak stress is still 25-28 % low, because it lives at a curved
boundary where constant-strain triangles are at their worst.  This is not a bug, it is
what P1 elements do.  A design loop that ranks candidates by coarse peak stress is
ranking them by a number that is biased, and biased *unevenly* across designs.  The
surrogate's job is to sit on the coarse mesh and output the fine answer.

The learning target is therefore the fine von Mises field **interpolated onto the
coarse nodes** (barycentrically, through the actual fine triangulation, so values are
never interpolated across a hole).  Every metric is reported against three references:

- **coarse FEM as-is** — the baseline to beat, for the price of a coarse solve.  Over
  the 400-design training set it under-predicts the peak by **35 %** on average, worse
  than the 12-design table above: the tail of tight-ligament designs is where coarse
  meshes fail hardest, and it is exactly the tail a lightweighting study walks into;
- **the surrogate**;
- **the interpolation floor** — the error a *perfect* nodal model would still have,
  measured at **-10.5 %**.  Reporting a surrogate without that floor makes it look
  better than physics allows.

That floor is worth decomposing, because it is not what it first looks like.  The
quantity of interest is the peak *element* von Mises of the fine solve.  Averaging
element stresses onto nodes — standard practice, since P1 element stresses are noisy —
already loses ~8 % of the peak at h = 0.010 (the `nodal vs elem` column of
`01_validate_fem.py`); sampling that nodal field at coarse node positions loses only a
further ~2 %.  So the floor is dominated by a *representation* limit, not by mesh
coarseness, and no nodal-field model can get past it.

That is why every model here also carries a **graph-level head** that regresses the
peak directly, bypassing the field entirely.  Both numbers are reported — `peak err`
from the head, `peak-from-field err` from the maximum of the predicted field — so the
difference between them is visible rather than quietly chosen.

### Verification

`tests/test_fem.py` runs the standard checks before anything is learned: a
constant-stress **patch test** (uniform tension reproduced to 1e-9 with roller
supports), an **energy balance** (external work = twice the strain energy, to 1e-9),
linearity, zero-load, clamped-node kinematics, element areas against the analytic
material area, and monotone convergence of the peak stress under refinement.

## 2. Why a graph network

The number of holes, the node count and the connectivity all change from sample to
sample, so there is no fixed tensor to convolve.  `stressgnn/models/gnn.py` is a
MeshGraphNet-style encode-process-decode network: message passing on the mesh edges,
relative node positions as edge features, node-type one-hots, the load vector, and the
local element size (the cue the network needs to know *which* discretisation it is
looking at).

Two knobs are swept rather than tuned quietly, because they are the two things that
decide whether this works on a stress field:

- **`n_message_passing`** — information travels one edge per block.  A load on the
  right edge is ~40 edges from the far side of the plate, so a 5-block network
  structurally cannot see it.  The sweep (0, 2, 5, 10, 15) makes that visible;
  `n_message_passing = 0` degenerates to a pointwise MLP and is included as the
  "how much of this is just local?" control.
- **`use_global`** — a global latent, pooled from and broadcast to every node in each
  block, gives an O(1)-hop shortcut for that long-range coupling, far cheaper than
  stacking 40 blocks.

Two variants change the problem rather than the architecture:

- **`-corr`** feeds the coarse FEM solution in as a node feature.  The model is then a
  discretisation-error correction rather than a pure surrogate — you pay for the
  coarse solve (which you were paying anyway) and ask the network only for the part
  the mesh is missing.
- **`-maxloss`** adds an explicit loss term on the per-part peak stress, because a
  plain nodal MSE has no particular reason to get the one node an engineer cares about
  right.

### The grid baseline

`stressgnn/models/cnn_grid.py` rasterises the part onto a 192x96 image, runs a U-Net,
and samples the prediction back at the mesh nodes.  It is given a fair shot — the grid
spacing matches the fine element size, and the loss is evaluated at exactly the same
nodes as for the graph models — so any gap is attributable to the representation
itself.  It is there to be argued with, not dismissed: "why not just voxelise it" is
the first question anyone asks.

## 3. Generalisation is tested, not assumed

| split | what changes |
|---|---|
| `test` | new geometries, coarse mesh size drawn from the training range |
| `res` | the *same* designs re-meshed at h = 0.025, a resolution never seen in training |
| `ood` | 4-6 holes (training tops out at 4) and load angles from a different quadrant |

The `res` split is the one that matters for the claim of discretisation invariance: if
the network has merely memorised one mesh density, it fails there while looking
excellent on `test`.

## 4. Design selection

`scripts/04_optimize.py` — the experiment the rest of the repo exists to support.

A design loop does not need exact stresses; it needs the **ranking** of candidates to
be right, so that the design it keeps is genuinely the best one.  So the script draws
candidate hole layouts at constant removed area (a lightweighting study), scores each
one three ways — fine FEM (ground truth, computed only to grade the others), coarse
FEM, and the GNN on the coarse mesh — and then reports a decision rather than an
accuracy:

- **Spearman correlation** of each cheap score against the truth;
- **regret** — how much worse the design each strategy would have made you pick is
  than the true optimum, both for its top-1 pick and for a verified top-3 shortlist;
- **cost per design evaluation**, measured end to end, meshing included.

That last point is worth stating plainly: once the solve is replaced, **meshing
becomes the bottleneck**.  GNN inference is a few milliseconds against ~150 ms of
meshing, so the honest speed-up of this pipeline is set by the mesher, not by the
network.  In an industrial setting that is the argument for surrogates that consume
CAD-derived meshes directly instead of remeshing per iteration.

## 5. Limitations

- Linear elasticity, plane stress, small strain, one material.  Nothing here transfers
  directly to contact, plasticity or buckling.
- The geometry family is circular holes in a rectangle.  Richer topology (fillets,
  slots, non-convex outlines) would stress the graph representation much harder.
- Uniform element size per mesh; production meshes are graded, and graded meshes are
  where the local-size feature would really earn its place.
- The reference is a converged *discretisation*, not an experiment — the surrogate
  learns the FEM, and the FEM's own model error is out of scope.

## 6. Running it

```bash
uv venv --python 3.12 .venv && VIRTUAL_ENV=.venv uv pip install -e .
./.venv/bin/python run_all.py            # everything, ~50 min on an M-series laptop
```

or step by step:

```bash
python scripts/00_generate_data.py       # ~20 min  -> data/
python scripts/01_validate_fem.py        # ~2 min   -> results/fem_convergence.json
python scripts/02_train_all.py           # ~25 min  -> runs/
python scripts/03_report.py              #          -> RESULTS.md, figs/
python scripts/04_optimize.py            # ~6 min   -> results/optimization.json
python -m pytest tests -q
```

`scripts/02_train_all.py --epochs 15 --skip-ablations` gives a smoke run in ~3 min.

## 7. Layout

```
stressgnn/
  geometry.py    hole layouts, validity constraints, load cases
  mesh.py        gmsh meshing, node tagging, boundary extraction
  fem.py         vectorised CST assembly, sparse solve, von Mises, interpolation
  dataset.py     fine/coarse solve pairs, packing, graph construction, rasterisation
  models/        gnn.py (MeshGraphNet), cnn_grid.py (grid baseline)
  train.py       shared training loop
  evaluate.py    field / peak-stress metrics against the three references
  plots.py       figures drawn on the mesh
scripts/         00 generate, 01 mesh convergence, 02 train, 03 report, 04 design selection
tests/           FEM verification, meshing, graph construction
```
